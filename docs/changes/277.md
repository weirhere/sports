## Decision

**A PR shepherd babysits open PRs on a half-hourly schedule, and it is off until a repo variable turns it on.** `scripts/pr-shepherd.sh` merges main into a conflicting branch and keeps both sides of a docs-ledger conflict; on a failed check it compares the failing tests with main's latest run of the same workflow, re-runs a flaky one once per head commit, and hands a real failure to `claude -p` with tools that can only edit tests and snapshots; it enables squash auto-merge where it's off and posts one comment per pass that did something. Anything touching product code — a conflict outside the ledgers, a build error, a fix that strays — gets the `needs-human` label and the shepherd leaves that PR alone until a person removes it. There is no force-push and no admin merge in the script; `git push` and `gh` are disallowed tools for claude. The workflow is gated on `vars.PR_SHEPHERD_ENABLED`, refuses a live run without a PAT, and `workflow_dispatch` defaults to dry run.

## Why

The PR flow is already "open, auto-merge, watch CI", and the watching was the part that cost a session's attention: a ledger conflict or a flaky iOS run left a finished PR sitting until someone looked. The shepherd does the mechanical half and draws a hard line at the judgment half, because an automated pusher that can touch product code is a reviewer nobody appointed. The flakiness test is "does main fail the same way" rather than a retry budget, since a retry that passes proves nothing about a test that fails on main too. The PAT requirement is a GitHub fact, not a preference: pushes made with the built-in token never trigger `pull_request` workflows, so the shepherd's merge would strand the PR it meant to help. Gated rather than live on merge so the dry run is the thing that decides.
