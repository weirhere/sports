## Decision

**A pro's player page names their college, and the row opens the school.**
NFL, NBA and NHL Profile cards gain a College row between Position and
Jersey, from `college: {id, name, shortName}` on the roster row or the athlete
payload, whichever door the page came through. The row links to the school's
college football team page when the directory has it. A school without FBS or
FCS football stays plain text, and college football players get no row.

## Why

ESPN carries the field on both payloads the player page already reads (probed
2026-11-02: every NFL and NBA roster row, about half an NHL roster, absent for
anyone who didn't go), so it costs no request. The college id is the school's,
the same value as its college football team id (UNC 153, Florida State 52,
UMass 113). That makes the link a directory lookup, not a mapping table. A
college player's school is already the team badge over the card, so a row
would only repeat it.

## Web parity

shipped — `playerProfileRows` adds the row, and the player route resolves the link against the FBS and FCS standings on the server.

## Decision

**College team pages get a Pros tab, built from a weekly file rather than on
device.** After Roster: the school's players now in the NFL, NBA and NHL, one
card per league, each row pushing the player page, hidden when the school has
none. `scripts/build-pros.py` walks the 94 pro rosters and indexes them by
college id into `pros.json`, which is bundled and served at
statside.co/pros.json. `.github/workflows/pros.yml` rebuilds it every Tuesday
and arms auto-merge on the PR when `PR_SHEPHERD_TOKEN` is set.

## Why

The reverse lookup needs every pro roster, ~18 MB of JSON. That's a poor
trade for one tab visit on a phone, and `coaches.json` already showed the
served-file pattern works (Andy's call, 2026-11-02). The first run found
3,211 players from 296 schools. All 83 schools that matched no FBS/FCS team
are schools without football, which confirms the id-sharing finding across
every player, not just three. The ~650 KB file is decoded off the main
thread, because `RootView` builds its stores at launch. A PR opened with
`GITHUB_TOKEN` triggers no workflows, so the required checks would never run
and auto-merge would never fire. That is why the weekly PR is opened with the
shepherd's token when there is one.

pending — the web can read the same `/pros.json`; the tab itself isn't built there yet.
