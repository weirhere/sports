## Decision

**Pixel baselines for the surfaces Andy iterates on by eye, and a workflow for every UI change from here on.** `sportsTests/Snapshots/ComponentSnapshotTests.swift` snapshots the Starters card (`FormationCard`), the game header in both states (`GameHeader`, `CompactGameHeader`) and the Scores day strip (`DayStrip`) on an iPhone 17 Pro and an iPhone SE, light and dark, with football, basketball and hockey data — 48 PNGs, committed beside the test and recorded on the iOS 26.5 iPhone 17 Pro simulator. The test target takes its first dependency for it, pointfreeco/swift-snapshot-testing 1.19.6, test-only: the app, the widget and the zero-dependency rule are untouched. The suite is gated on `STATSIDE_SNAPSHOTS=1` so CI's runner, on whatever runtime it gets, skips it rather than failing on a font hint. Two small refactors made the surfaces renderable without a screen: the game page's header became its own view (`GameHeader`, with `init(game:summary:)` on it and on `CompactGameHeader` so both read the same merge), and `DayStrip` takes a `now` so "Today" can be a fixed date. The workflow is `.claude/skills/ui-change/SKILL.md`: write the expected visual outcome first, implement, `scripts/snapshot-tests.sh --record --filter <test>` for only the affected baselines, `scripts/ui-report.py` for a before/after page in `/tmp/ui-report`, `scripts/verify-sim.sh` for a screenshot of the installed build on the dedicated "iPhone 17 Pro snapshot-tests" simulator, and up to five rounds against the written expectation before asking.

## Why

Andy, 2026-10-19, in so many words: *"for any UI change I request: write down the expected visual outcome first; implement it; re-record only the affected snapshots; generate a side-by-side before/after HTML report in /tmp/ui-report; and verify the installed build on a dedicated simulator by screenshot. If the result doesn't match my description, for example a divider in the wrong place or uneven padding, iterate up to 5 times before asking me."* The 2026-10-18 Roster day was the case for it: a dozen spacing rows settled by looking, each re-verified by hand on a shared simulator another session might have just reinstalled. A baseline makes "re-record only the affected snapshots" a statement about what else *didn't* move, which is the half of a UI change nobody looks at. Device layouts rather than device runs: the library lays a view out at a config's width, scale and traits, so one simulator renders both phones and the SE needs no runtime of its own. Hand-built fixture data rather than the ESPN captures so a refreshed payload can never move a baseline, and every URL nil so no fetch races the render. The first comparison pass earned its keep before the PR opened: the live dot's pulse was captured four shades apart on the football headers, so the renders freeze it with the switch the share card already used.
